## Trusted Environment Bootstrap (RISC-V) — bootstrap

## 1. Назначение документа

Документ описывает концепцию, цели, ценность и границы проекта **bootstrap** — доверенной пошаговой среды сборки для RISC-V (rv64gc), которая следует дорожной карте [live-bootstrap `parts.rst`](https://github.com/fosslinux/live-bootstrap/blob/master/parts.rst) и поставляет миниатюрное самохостящее ядро (`simon`), способное компилировать и исполнять каждую следующую стадию прямо изнутри себя. Документ служит ориентиром для команды, преподавателей и внешних рецензентов.

---

## 2. Предпосылки и мотивация

Современные тулчейны опираются на слои уже существующих бинарников, происхождение которых редко поддаётся аудиту. Для системы, претендующей на «доверенность», это самое слабое звено: то, что нельзя прочитать руками, нельзя и обосновать.

`live-bootstrap` предлагает лестницу постепенно расширяющихся языков (`hex0 → hex1 → hex2 → M0 → M1 → M2 → cc_*`), где каждая стадия достаточно мала, чтобы её проверить глазами, и достаточно выразительна, чтобы описать следующую. Наш проект переносит эту идею на RISC-V (rv64gc) и дополнительно встраивает лестницу *внутрь работающего ядра*, так что «собрать следующую стадию» — это команда шелла, а не шаг билд-системы.

Проект преследует образовательную, исследовательскую и инженерную цели:

- глубоко понять загрузку, линковку и цепочку доверия, реализуя каждый уровень своими руками;
- удерживать воспроизводимость и минимальные внешние зависимости;
- экспериментировать с ранней загрузкой как в QEMU `virt`, так и на LicheePi 4A;
- сверяться с цепочкой live-bootstrap как с эталонной дорожной картой.

---

## 3. Общая цель продукта

Проект `bootstrap` обязан обеспечивать:

- Воспроизводимый загрузочный образ RISC-V, собранный из трёх стадий: `boot` (декодер hex0) → `simon` (ядро) → FS-полезные нагрузки (hex0/hex1/hex2/M0).
- Минимальное ядро (`simon`), внутри которого живут шелл (`sish`), in-memory ФС и последовательность встроенных компиляторов (`hex0`, `hex1`, `hex2`, затем `M0`).
- Рабочую цепочку вплоть до **M0** — первой стадии, вводящей настоящие ассемблерные мнемоники, точно перенесённой из live-bootstrap.
- Запуск на QEMU `virt` (основная цель разработки) и на LicheePi 4A (аппаратная валидация).

Каждый milestone даёт:

- определённую входную среду,
- проверяемый артефакт на языке следующей стадии,
- критерий приёмки, наблюдаемый через UART.

## 5. Проблемное поле и потребности

| Проблема | Как проект её решает |
|---|---|
| Современные тулчейны содержат непрозрачные бинарники, которые невозможно проаудировать. | Доверенный корень ограничен однократным использованием кросс-компилятора; все последующие стадии порождаются *внутри* цепочки. |
| Билд-системы скрывают реальный порядок компиляций. | Порядок сборки делается явной, видимой пользователю шелл-сессией внутри `simon`. |
| Загрузку RISC-V тяжело понять только по документации. | Каждая стадия мала, самодостаточна и наблюдаема в рантайме через UART. |
| Расхождение поведения железа и эмулятора. | Параллельные builder-ы (`builder-mvp`, `builder-lichee`, `builder-syscall`, …) фиксируют снимок цепочки для каждой цели. |

## 6. Цели проекта

- Поддерживать доверенную трёхстадийную цепочку загрузки на RISC-V (`boot` + `simon` + FS-полезные нагрузки).
- Сохранять у `simon` способность собирать каждую следующую стадию live-bootstrap *изнутри работающего ядра*.
- Доставить hex0 (готово), hex1 (готово), hex2 (в работе) и **M0 (актуальный milestone)**.
- Загрузить ту же цепочку на LicheePi 4A.
- Покрыть каждый поставляемый builder интеграционными тестами `pytest + pexpect` против QEMU.
- Документировать архитектуру (SAD), требования (SRS) и дорожную карту (Vision, Project-Schedule) в `docs/`.
- Зафиксировать версию тулчейна и продемонстрировать побайтовую воспроизводимость образа на двух хостах.

## 7. Ключевые характеристики и функциональность

| Функция | Описание |
|---|---|
| Трёхстадийный образ | Плоская конкатенация `boot.bin + simon.hex0 + FS-файлы`, грузится через QEMU `-bios`. |
| Встроенная ФС | `simon` разбирает FS-данные при загрузке и выставляет файлы через `ls`. |
| Шелл `sish` | Шелл по UART с командами `ls`, `echo`, `do`, `hex0`, `hex1`, `shutdown`, `reboot`, `debug`. |
| Встроенные hex-компиляторы | `hex0` (готово), `hex1` (готово), `hex2` (в работе) — все реализованы внутри `simon.S`. |
| M0 (порт live-bootstrap) | Цель текущего milestone-а: исходник M0, собранный встроенным hex2 и исполнённый через `do`. |
| Поддержка нескольких целей | Та же цепочка работает на QEMU `virt` и LicheePi 4A (`builder-lichee`). |
| Интеграционные тесты | `pytest + pexpect` управляют реальной QEMU и сверяют ответы по UART. |
| Документация | `SAD.md`, `SRS_bootstrap(ENG/RU).md`, `Vision(ENG/RU).md`, локальные `README.md` и `parts.rst` каждого builder-а. |

## 8. Область и границы (Scope)

**Включено (v0.2):**

- Полная цепочка hex0 → hex1 → hex2 → M0 на RISC-V rv64gc.
- QEMU `virt` как основная цель разработки и CI.
- LicheePi 4A как валидационная цель для загрузочной цепочки.
- Интеграционные тесты на `pytest + pexpect`.
- Документация по стадиям и по builder-ам.

**Не включено (v0.2):**

- Полноценная ОС.
- Сетевой стек, дисковые драйверы (за пределами UART и встроенной ФС).
- Стадии за пределами M0 (M1, M2, `cc_riscv64` — явно будущая работа).
- Stage 0 — кросс-компилятор принимается как доверенный корень.
- Планирование процессов в основном ядре (живёт в `builder-syscall` до запуска M0).

## 9. Критерии успеха

- Чистый checkout даёт рабочий `image_qemu.bin` в `builder-mvp` через `make build-and-run`.
- `builder-hex1` компилирует и запускает hex1-полезную нагрузку изнутри ядра (покрыто тестами).
- **`builder-hex2` собирает M0 из hex2 и успешно исполняет полезную нагрузку, произведённую M0, в QEMU.**
- Та же цепочка доходит до `Hello, World!` на LicheePi 4A.
- `SAD.md`, `SRS_*`, `Vision_*` соответствуют текущему состоянию кода.
- Две сборки `make clean && make` (одинаковый тулчейн) дают идентичный `image_qemu.bin`.

## 10. Основные риски

| Риск | Митигирующая мера |
|---|---|
| Дизайн M0 расходится с upstream live-bootstrap | Считать upstream-M0 спецификацией; портировать, а не переизобретать. |
| Обновления тулчейна или QEMU ломают воспроизводимость | Фиксировать версии в `README.md` builder-а. |
| Особенности железа LicheePi 4A инвалидируют образ, настроенный под QEMU | Держать `builder-lichee` отдельным снимком, пока цели не сойдутся. |
| Процессная модель из `builder-syscall` конфликтует с пост-M0-ядром | Откладывать реинтеграцию до полного запуска M0. |
| Документация устаревает быстрее кода | Сделать «доки отражают текущий код» частью критериев приёмки каждого milestone-а. |

## 12. Заключение

Проект `bootstrap` — это «руками» написанное, родное для RISC-V прочтение идеи live-bootstrap: цепочка доверия, объясняющая саму себя и достаточно маленькая, чтобы её можно было проверить на каждом шаге. За счёт встраивания цепочки в работающее ядро последовательность сборки превращается в прозрачную шелл-сессию, а не в чёрный ящик билд-системы. Текущий milestone — запуск M0 — это первая точка, в которой цепочка начинает производить настоящий ассемблер изнутри той системы, которую она же и поднимает; это вход в остальную часть лестницы live-bootstrap.
